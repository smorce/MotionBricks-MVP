# チェックポイント01：停止準備 → F001接続のアーキテクチャ仕様

作成日：2026-11-03。対象ブランチ：`checkpoint-01`。
対象は現在の実装と、固定した5種類の目視確認パターン。

## 1. このチェックポイントの位置づけ

通常の床クリックに対して、歩行中に進路を調整し、停止準備からF001の停止モーションへ接続する。
元のクリック位置へ厳密に合わせることより、歩いてきた方向に沿って自然に停止することを優先する。
位置誤差は5cm以内を設計上の許容値とし、位置合わせだけの追加ステップを避ける。

ユーザーから現在の状態について「かなり良い」との評価を得たため、ここを復帰可能なチェックポイントとして保存する。
これは全入力・全歩行状態の自然さを保証する承認ではない。個別の候補には未評価のものがあり、
固定データに各候補の人間評価を自動的に付けない。停止条件の追加調整はいったん保留する。

**コードによる停止条件は、自然さの判断基準としてはあまり信用していない。**
人間の感覚と一致しないことが既に分かっているため、数値を満たすことを改善の最終目的にしない。
`accepted`、`settled`、到着誤差ゼロ、接地検証合格は、実装上の状態または機械的な測定結果であり、
「自然に止まった」という意味ではない。逆に、コードが拒否した候補も、拒否理由を残して人が再評価できるようにする。
自然さの最終判断は、実際のロゼVRMで歩行から停止までを連続再生して行う。

## 2. 対象と非対象

- 通常画面の既定方式は `prepared`（停止準備 → F001接続）。旧クライアントの従来方式指定もこの方式へ移す。
- 以前の実験である `visual`（目視11候補・厳密一致）は比較用に残す。従来停止制御は通常画面の選択肢にしない。
- 既存の特定の到着動作、VRMリターゲット、姿勢調整は維持する。
- このチェックポイントでは、停止条件だけによる自然さの最適化、全状態での到着保証、VRM靴底の厳密な物理シミュレーションを行わない。

## 4. 移動要求から停止まで

1. ブラウザはクリック位置と、現在表示しているフレームの連番・移動要求IDを送信する。
2. バックエンドは配信済みチェックポイントを照合し、姿勢、履歴、接地、移動状態を復元する。
3. 歩行中は元の目的地を保持し、実測した進行方向と横ずれを使って方向指令を調整する。
4. 停止候補の準備に入っても、横ずれが許容値を超えていれば停止開始を見送る。
5. 停止開始時の進行方向を固定し、その直線上へ元のクリック位置を射影してF001生成用の目標を作る。
6. 推論側は接続元姿勢・履歴を使い、別の生成用キャラクターでF001区間を生成して検証する。
7. 未採用候補は再生せず破棄する。歩行を進めた接続元から再試行し、採用済み区間は確定フレームとして配信する。
8. ブラウザは受信時刻ではなくシミュレーション時刻を使って補間し、停止区間と待機への移行を表示する。

元の目的地 `goal` と生成用目標 `final_stop_goal` は別の値。
生成後にフレーム全体を平行移動して目的地へ合わせる処理は入れない。
到着位置合わせだけを目的とする追加停止区間は作らない。

## 5. 歩行進路と停止開始の現在値

| 項目 | 現在の実装 |
| --- | --- |
| 到着許容誤差 | 元のクリック位置から5cm |
| 進行方向推定 | 直近12ルート位置の変位。変位5cm超かつ平均速度0.5m/s超で更新 |
| 低速時の方向 | 直前の有効方向を保持。未取得なら現在の向きを使用 |
| 方向指令 | 初期ルート方向、横ずれ、目的地方向と実測進行方向の差を合成 |
| 指令の旋回上限 | 2rad/s |
| 歩行再生成の方向差閾値 | 1度 |
| 停止準備距離 | 1.2m以内 |
| 未一致時の停止開始距離 | `min(1.2m, 0.9m + 速度 × 0.15秒)` |
| 停止開始時の横ずれ | 実測進行方向に対して5cm以内 |
| 未再生候補の再試行 | 最大16回のプレビュー拒否を許し、各回の間に少なくとも歩行更新を挟む |

評価済みA方式候補の厳密照合が成立する場合はそれを優先する。
未一致の場合は姿勢履歴・速度・支持状態・接地・距離による近さからA方式候補を選び、
`human_rating=unknown` の実験候補としてF001接続を試す。
これらの閾値・類似度は実装パラメータであり、人間の感覚を表した確定仕様ではない。

## 6. F001生成と足の扱い

公式モデルで停止目標へ接続するA方式を使う。歩行中の履歴を利用し、生成用状態を表示中の状態と分離する。
F001停止は足を一切動かさない方式ではないため、全区間で同じ支持足を固定する検証は適用しない。

公式接地信頼度0.5以上、校正した床からの足高さ2cm以内を接地アンカー取得の目安とする。
接地中は公式IK補正器へアンカーを渡し、離地時は4フレームで補正を解除する。
床への侵入がある場合は足のIK目標を調整し、表示ルート全体は動かさない。
独自の骨伸縮による帳尻合わせは行わない。

補正後の区間について、接地滑り、床、骨長、膝、関節連続性、終端安定性などを検証する。
接地滑りの閾値2cm、離地高さの閾値2.5cmは維持する。接続元ですでに浮いている足の高さも集計する。
進行検証では、大きく通過して戻る動作を抑止しつつ、目的地の5cm許容円内の体重移動を許す。

現在の採用処理はこれらの検証を実行するが、検証器の判定自体も改善対象である。
拒否理由は生成品質の根本原因と同義ではない。拒否された場合も、入力状態、補正、検証値を切り分けて調べる。

## 7. 並行実行と滑らかな再生

GPU推論は `spawn` した単一プロセスで直列実行する。
親側は確定フレームを受け取り、Windowsの高分解能タイマーを使って60Hzで配信する。
重い停止生成を配信の同じループで同期実行しない。

親側のバッファは最大240フレーム、初期充填は180フレーム。
終端状態が先に到着した場合は充填数を待たず再生を開始する。
プロセス間出力キューは120件。先行生成により待ち時間を吸収する設計であり、
100msのブラウザ補間だけで推論遅延を解決する構成ではない。
要求直後の準備待ちは残り得る。推論が確定済み区間を消費する速度に追いつかなければ保持が発生し得る。

ブラウザは100ms遅延の時刻バッファで位置・回転を補間する。
フレーム欠損時に無制限な外挿をせず、最後の確定姿勢を保持する。
再開時は保持した時刻から再同期し、古い初期スナップショットによる恒久的な遅延を防ぐ。

## 8. 一貫性と再クリック

配信フレームには `sequence`、`simulation_time`、`gait.move_id` を付ける。
ブラウザからの移動要求は `source_sequence` と `source_move_id` を指定する。
親側は直近240件の配信済みチェックポイントを保持し、指定された接続元と一致する状態から再生成する。

新要求が来ると旧要求のバッファを破棄する。推論結果の要求IDが現在の要求と異なれば採用しない。
接続元が失効して照合できない場合は、その要求をエラーとして拒否し、推測した状態へ接続しない。
この単発拒否は、後続クライアントへ恒久的なエンジン障害として再送しない。
未検証の停止区間へ切り替える処理は入れない。

## 9. 失敗状態と可観測性

自然な停止をコードが認定することはできないが、採用できる区間が得られない場合は `stop_failed` として記録する。
`settled` は機械的な到着・接地条件を満たした状態名であり、人間評価の成功とは区別する。
従来の停止探索へ自動的に戻して成功扱いにしない。

歩行更新、候補照合、停止生成、F001推論、診断、保存、JSON化、送信、描画を分けて計測する。
`GET /performance` で段階別情報を取得し、ブラウザから `POST /performance/render` へ描画情報を送る。
大きな姿勢履歴・レビュー資料を毎フレームの選択情報から除き、詳細リプレイは別の保存スレッドへ渡す。
保存キュー上限は8件で、満杯時は詳細記録を落として回数を計上する。保存完了を待って配信を止めない。

## 10. 人間による確認経路

通常画面上部から `/stop-distance-lab.html?prepared` を開く。
固定した公式モデル生成結果とロゼVRMを自動読込し、追加推論なしで反復再生する。
パターンは小さな斜めずれ約74cm、直進2m、旋回後2m、短距離約30cm、斜め接近約1.4mの5種類。
別々の入力状態から生成した例であり、同じ歩行状態に対する5候補の比較ではない。

条件選択、正面／側面／斜め、0.25／0.5倍速、時間スライダー、停止開始・Idle移行への移動を用意する。
全候補表示の時点ジャンプは先頭候補のイベント時刻を使うため、詳細確認では1条件を選ぶ。
短い候補は最終姿勢を保持する。緑の輪は元のクリック位置。
人間の評価・時刻・メモはブラウザに保存し、JSONで書き出せる。機械検証の合否とは独立して扱う。
操作手順は [F001接続の目視確認](f001-preview-review.md) を参照。

## 11. 検証範囲と既知の限界

チェックポイント時点でPython 184件、JavaScript 37件のテストが通過。
5種類の固定データについて、全姿勢、目的地、停止開始イベント、終端誤差の整合性を検証した。
実ブラウザで自動読込、5条件表示、単一条件への切替、時点ジャンプ、スロー再生、視点変更、
評価の永続化・書き出しを確認した。これらは機能確認であり、歩容の自然さの自動評価ではない。

同一端末での過去の60秒比較では配信停止の削減を確認しているが、計測は段階別の実装時点のもの。
現在の全変更について、全入力で100ms超の停止がゼロという保証には使わない。
以前の連続クリック試験には旧2cm進行条件による拒否が残っている。
その後の5cm許容円の修正と固定5例の確認をもって、連続クリックの全状態を確認済みとはしない。
記録の範囲は `metrics/natural-arrival/verification-summary.json` を参照。

## 12. 設計判断と今後の変更基準

- 完全一致ではなく5cmの誤差を許し、停止モーションへ横方向の位置合わせを押し付けない。
- 停止開始時に方向を固定し、生成後のルート平行移動による見かけ上の成功を避ける。
- 推論と配信を分離し、確定済みデータを先行供給する。遅延時の準備待ちと、再生中の停止は分けて測る。
- 元のクリック位置、生成用目標、機械検証、人間評価を別々に保持し、原因を追跡できるようにする。
- 次の改善は人間の評価した候補・時刻・視点を起点にする。数値合格率を上げるためだけの条件調整は行わない。
- 検証器を変更する場合は、実際に良く見える例と悪く見える例の両方を残し、改善前後を同じデータで比較する。
