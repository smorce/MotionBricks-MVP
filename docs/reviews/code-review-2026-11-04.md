# Codexコードレビュー（2026-11-04）

## 対象・結論

MotionBricksMVPの現行バックエンド、Webクライアント、仕様書、関連テストを中心に静的レビューした。ローカル専用の実験用MVPとして評価する。旧版 roze_scene_preview_port_v0.2 は現行実装の評価対象から除外した。全ファイルを逐行精査した監査ではない。

| 軸 | 評価 | 根拠 |
| --- | --- | --- |
| Performance | C | 推論の別プロセス化、有界フレームバッファ、非同期保存は良い。一方、入力・ルーティング・配信タスクの負荷制御が一貫せず、履歴コピーと描画診断の費用も残る。 |
| Cleanliness | C | 状態管理と停止選択の分割、仕様・回帰テストがある。一方、主要ファイルに多数の責務が集中し、通信契約が未型付けで起動手順にも不一致がある。 |
| Security | D | ループバック限定は有効だが、WebSocketのOrigin確認と認証、入力検証がない。悪意あるWebページからローカルエンジンを操作できる経路が残る。 |

評価基準：A＝十分な設計と検証実績、B＝軽微な改善のみ、C＝MVPとして成立するが重要な改善あり、D＝重大な境界管理不足、E＝利用継続を阻む問題。実測性能、依存パッケージの既知脆弱性、動作の自然さは未評価であり、この評点から保証しない。

## 改善点

### 1. WebSocketの接続元を検証しない

- 重要度：高／Security
- 該当：`backend/server.py:83`、`:163`〜`:166`
- 根拠：HTTP向けCORS設定はあるが、WebSocketはOriginを確認せずacceptする。認証処理もない。ループバックへのバインドだけでは、ブラウザからの不正なローカル接続を防ぐ設計にならない。
- 影響：ブラウザ側のローカルネットワーク制限等に依存するものの、許可していないサイトから移動要求、ログ・姿勢受信、計算負荷発生が可能な構造。
- 推奨：accept前にOriginを完全一致で検証し、必要なら短期セッション認証を追加する。欠落Originの扱いも明文化する。
- 検証案：許可Origin、別Origin、Origin欠落を分けた接続テスト。不正接続ではキューを更新しないことを確認する。

### 2. 入力の型・有限値・範囲・構造が未検証

- 重要度：高／Security・Cleanliness
- 該当：`backend/server.py:109`、`:175`〜`:186`
- 根拠：receive_jsonの結果へ直接getを呼び、座標をfloat変換してキュー投入する。配列、欠落座標、不正文字列の処理がなく、NaN・Infinityも有限値確認をしない。retarget_settingsとmetricsも構造を制限しない。
- 影響：接続ハンドラの例外終了、無効な数値の推論経路への流入、過大な入力による負荷。エンジン全体停止まで起こるかは未実証。
- 推奨：メッセージ種別ごとのスキーマ、有限値・座標範囲・列挙値・サイズ制限を境界に設け、英語の安定したエラー応答を返す。
- 検証案：配列、null、欠落値、非数値、非有限値、巨大metricsを投入する単体テストを追加する。

### 3. 要求・ルーティングのバックプレッシャー不足

- 重要度：高／Performance・Security
- 該当：`backend/server.py:22`、`:148`、`:186`、`backend/engine.py:495`、`:509`
- 根拠：commandsとpendingは無制限キュー。moveごとにタスクを作成し、to_threadで同期HTTP処理へ渡す。古い要求の結果は無視するが、その計算自体の取消・同時実行制限がない。D3の既定タイムアウトは60秒（`backend/d3_router.py:15`）。
- 影響：連打・複数接続・D3遅延時に待ちタスクと要求が蓄積し、通常の移動や終了処理にも遅延が及ぶ可能性。
- 推奨：最新moveの集約、有界キュー、接続単位の流量制限、D3同時実行数の上限を導入する。制御メッセージは移動要求と区別する。
- 検証案：D3をスタブ化し、連続入力時の保留数・最大メモリ・最新要求の処理時間を測る。外部APIへの負荷試験は不要。

### 4. 配信タスクに上限と終了時の管理がない

- 重要度：中／Performance・Cleanliness
- 該当：`backend/server.py:42`〜`:57`、`:64`〜`:67`
- 根拠：publishごとにbroadcastタスクを生成し、各接続へ逐次送信する。接続ごとの50msタイムアウトはあるが、タスク全体の容量制限や終了時の回収がない。
- 影響：低速接続が多い場合にタスクが重なり、同一接続への複数送信とイベント順序の扱いが複雑になる。実際の順序逆転は未再現。
- 推奨：接続ごとに単一送信ループと有界キューを持たせる。姿勢フレームの破棄方針と、状態イベントの保持方針を明記する。

### 5. 全履歴コピー・プロセス間転送の費用

- 重要度：中／Performance（要計測）
- 該当：`backend/engine.py:655`〜`:656`、`backend/frame_pipeline.py:84`以降のProcessOutput.offer、CheckpointHistory
- 根拠：チェックポイントに姿勢と履歴のnumpyコピーを作成してプロセス間キューで転送し、最大240個の配信済みチェックポイントも保持する。
- 影響：履歴長・骨格サイズに応じてコピー、シリアライズ、メモリの費用が増える。現状でボトルネックであるとの断定はしない。
- 推奨：履歴バイト数、コピー時間、IPC時間、保持メモリを分離計測する。必要なら共有リングバッファや履歴参照の共有化を検討し、接続元の正確な復元を維持する。

### 6. 描画ループが診断を毎フレーム実行

- 重要度：中／Performance（要計測）
- 該当：`web/src/main.js:893`〜`:962`
- 根拠：毎フレーム姿勢補間に加え、updateMatrixWorld(true)、足・つま先のワールド座標取得とVector3生成、診断データ生成を行う。
- 推奨：描画と診断の所要時間を分け、診断の低頻度化、ベクトル再利用を比較する。診断停止で必要な状態遷移を壊さないことを確認する。

### 7. 通信・推論・画面制御の責務集中

- 重要度：中／Cleanliness
- 該当：`web/src/main.js:1`〜`:1027`、`backend/engine.py:1`〜`:898`、`backend/server.py:134`
- 根拠：main.jsに設定永続化、通信、クリック、姿勢所有権、描画、診断送信が集中する。engine.pyはプロセス協調と生成処理を同居させる。通信契約はdictと任意フィールドに依存する。
- 推奨：通信契約を仕様化し、接続管理・描画診断・プロセス協調を小さく切り出す。既存テストで振る舞いを固定してから構造変更し、機能修正と分ける。

### 8. 起動説明とテスト実行入口の整備

- 重要度：低／Cleanliness
- 該当：`README.md:57`、`web/vite.config.js:21`、`web/package.json:6`
- 根拠：READMEは5173へのアクセスを案内する一方、現行Vite設定は5188。package.jsonにはdevしかなく、既存のNodeテストを実行する標準スクリプトがない。
- 推奨：現行チェックポイントの起動手順へ統一し、通常の単体テストとGPU・実モデル検証の実行入口を区別して記載する。

## 良い点

- FramePipeline、ProcessOutput、CheckpointHistoryは容量制限を設けている。入力キューと対照的に、フレーム経路は負荷管理を考慮している。
- ReplayWriterは有界キューとドロップ・失敗数を持ち、保存を推論経路から外している。
- TIMINGSの計測値保持は有界。GaitLogにも上限とロックがある。
- D3の選択結果は候補IDと信頼度で検査し、通信失敗時にフォールバックする。
- 現行仕様は機械的な停止合格と人間の自然さの評価を区別し、固定再生をライブ検証の代用にしない。
